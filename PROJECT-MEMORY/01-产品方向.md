# 01 · 产品方向

## 产品是什么

**车市镜（EV-MarketLens）**是新能源汽车市场情报对话式 Agent。用户不需要理解数据库或检索系统，只需用自然语言提问：

- “2025 年纯电销量前十是谁？”→ Text2SQL 查询星型模型并生成图表和洞察；
- “购置税减免政策到什么时候？”→ RAG 检索文档并带引用回答；
- “销量变化结合政策怎么解释？”→ Text2SQL 与 RAG 并行，再合并事实和证据；
- 信息不足 → 追问澄清；
- 普通寒暄 → 轻量对话。

产品的一句话价值：**把找数据、做分析、读报告和补充研究放进同一个可追溯的 Agent 工作流。**

## 为什么做

用户是 2027 届毕业生，计划在 **2026 年秋招**投递。项目主要证明：

- 能把 LLM 能力落到真实数据和用户流程，而非只调用一次 API；
- 能设计 Agent 状态图、重试、并行、降级和异步任务；
- 能处理 Text2SQL 的安全与语义正确性；
- 能处理 RAG 的召回、重排、证据门控、引用和多租户隔离；
- 能做可复现评测、前后端产品化和部署工程。

目标岗位按匹配度排序：

1. 大模型应用 / Agent 工程师
2. AI 后端 / AI 平台工程师
3. RAG / 知识库应用工程师
4. Python 后端工程师（带 AI 项目优势）

项目不是为了证明研究型算法创新，也不应包装成大规模生产平台。

## 差异化

1. **双脑而非单路聊天**：结构化事实和非结构化证据由不同链路处理。
2. **真实 Agent 编排**：13 节点 LangGraph 包含重试环、并行 fan-out、deferred join、澄清和降级。
3. **正确性优先**：SQL 有 AST 安全护栏和结构/语义双层验证；RAG 有证据门控、typed 引用和向量血缘。
4. **缺数处理可解释**：空结果触发异步 `Research → Plan → Code ≤3 → Review`，并向用户持续报告进度。
5. **工程闭环**：JWT、多租户、生产注册/配额门禁、SSE、前端图表、评测、健康检查和生产 Compose 都有代码落点。

## 产品边界

以下口径已经确定，不能夸大：

- Text2SQL 的 60/60 是固定回归集，不是开放域 100% 准确率。
- 当前 RAG 报告验证本地检索、人工标注证据覆盖和负样本拒答，不验证最终生成答案 faithfulness，也不代表生产 PG。
- 无数据采集只有在 Review 允许时写入发起用户的私有 RAG，不直接回写销量事实表，也不自动重跑原 SQL。
- `seed_real.py` 的数值是合成演示数据，不是市场事实。
- MinerU 未接入；当前解析后端是 `lite`。
- 已具备生产化部署配置，但尚未完成真实云端 fresh-volume 端到端验收。

## 成功标准

在秋招投递前，项目至少应做到：

- 权威仓库 README、技术设计、流程图与代码一致；
- 本地一键启动、深度健康检查、后端测试和前端构建可复现；
- Text2SQL、RAG、意图和数据质量报告能从当前代码重跑；
- 候选人能独立解释核心链路、关键取舍、失败复盘和诚实边界；
- 云端完成 HTTPS 可访问的 fresh-volume E2E，或在简历中明确只提供本地演示录像。

## 已否决的叙事

- 纯固定 BI 看板：无法体现 Agent 工程；
- “通用任意数据智能平台”：范围过大，容易被问穿；
- 只做 RAG 聊天：同质化严重；
- 直接宣称生产级、高并发或企业级准确率：缺少真实流量和规模证据；
- 把预留的 MinerU、未来事实回写闭环写成已完成能力：与代码不符。
